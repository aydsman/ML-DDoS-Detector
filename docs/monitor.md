# Monitor-only runner and backend handoff

The runner connects the existing frame/window pipeline to a trusted saved model. It does not attribute sources, request blocks or contact a firewall. It has run live on the lab server NIC (see Start, stop and monitored interface); real model readiness and real-data accuracy remain separate.

```powershell
python -m ddos_detector.monitor --replay tests/fixtures/week2/synthetic-mixed-boundaries.pcap `
  --victim 10.10.10.10 --model results/demo-model --log results/monitor-demo.jsonl
```

Use a model package generated by the project's training command, a fresh log path and an existing output parent. A synthetic package is explicitly labelled `data_kind: synthetic` in the output. This example does not measure real detector accuracy.

## Start, stop and monitored interface

**Monitored interface.** The runner captures one interface, chosen with `--interface` (no default; `--replay` is the only other source). In the lab this is `enp0s8` on `ddos-server`, the internal `ddoslab` network (10.10.10.10/24) that carries client and attacker traffic. `enp0s3` is the NAT/management NIC and must not be monitored. `--victim` (default 10.10.10.10) selects which destination address counts as inbound; frames in both directions are read but only inbound IPv4 TCP/UDP/ICMP to the victim are used. Check the interface first with `ip -br a` and confirm the address is the lab one.

**Start and stop with the scripts (Linux, as root).** Copy `deploy/monitor.env.example` to `deploy/monitor.env` and set the interface, model folder and Python. Then:

```sh
sudo scripts/monitor-start.sh --dry-run   # prints the exact command, starts nothing
sudo scripts/monitor-start.sh             # starts in the background, new log name each run
sudo scripts/monitor-stop.sh              # stops it and checks the final log record
```

The start script refuses to run without root, if the interface does not exist, if the interface is the management NIC (`MONITOR_FORBIDDEN_INTERFACE`; `enp0s3` when the setting is missing, and an empty value is refused unless `MONITOR_ALLOW_ANY_INTERFACE=1`), if the model folder is missing, or if a monitor is already running. It writes `run-<UTC time>-<starter PID>.jsonl`, `monitor.pid`, `monitor.lock` and `monitor.stdout` under `MONITOR_LOG_DIR` (default `results/monitor`). `MONITOR_DURATION` makes a run stop by itself.

`monitor.pid` holds the process id and that process's start time. A process counts as the monitor only if the id, the start time and the command line (`ddos_detector.monitor`) all match, so a stale file or a reused id is never signalled. A file that is not `<pid> <start time>` is refused with nothing signalled. Start and stop take one lock (`monitor.lock`, wait `MONITOR_LOCK_WAIT`, default 10 s), so two starts cannot both pass the check. Start reports success only after the monitor has written its own first status record (`started`, `MONITOR_START_WAIT`, default 30 s); if the process exits or no record appears it reports failure, and in the second case stops the process it started.

The stop script sends SIGTERM only to a verified monitor, waits up to 15 s (`MONITOR_STOP_WAIT`), and then prints the last log line. It exits 0 only if that line is a `completed` status record. If the recorded process is already gone, it still reads the log: a completed last record gives exit 0 and an incomplete or missing log gives exit 1. It never sends SIGKILL. The scripts need Linux `/proc` and `flock`.

**Start by hand.** The scripts run this command. Use a fresh log name each run, because the log is created exclusively and an existing file is refused.

```sh
sudo PYTHONPATH=. python3 -m ddos_detector.monitor --interface enp0s8 --victim 10.10.10.10   --window 1 --model results/demo-model --log results/run-$(date +%Y%m%d-%H%M%S).jsonl --duration 100
```

Use the Python that has the project requirements installed (for example a virtual environment's `python`). Without `--duration` it runs until stopped. A bad interface, missing permission or unusable model exits nonzero with a message on stderr and no windows logged. Monitor-only is fixed: nothing in this runner changes traffic or contacts a firewall.

**Stop.** Wait for `--duration` to elapse, press Ctrl+C (SIGINT) in a foreground session, or send SIGTERM (what `monitor-stop.sh` does). A background job started from a script ignores SIGINT, which is why the script uses SIGTERM. The runner discards the incomplete window, writes a final `monitor_status` record and prints the summary. Exit code 0 with `status: ok` means the run ended normally; 1 means capture became unavailable; 2 means it never started. SIGKILL or a power-off leaves no terminal status record, so treat a log without one as incomplete.

**Health fields.** `processing_delay_s` on each live window is the time between the window ending and its record being written (about 1.0 s with the one-second grace period). `max_processing_delay_s`, `late_dropped`, `skips` and `gaps` are in the terminal status record and the printed summary. For live capture the terminal record also carries `kernel_packets` and `kernel_drops`, read from the capture socket's own counters (`PACKET_STATISTICS`) when capture ends. They count frames the kernel queued for the monitor and frames it dropped because the socket buffer was full. They are `null` for replay and when the counters cannot be read. Zero drops do not prove the NIC or the wire delivered everything. Backlog is not measured (`backlog` stays `null`); `max_processing_delay_s` is the nearest signal. Do not read a clean run as proof of complete capture.

## Lab validation (November 11) and what is real

Vince reported a 100-second live run on the lab server's internal interface. All 225 legitimate HTTP requests succeeded. The monitor scored 72 completed windows, reported zero late arrivals and recorded a maximum processing delay of 1.44 s. Raw artifacts are outside Git. This records a lab observation with a synthetic model.

| Stage | Real or replayed |
| --- | --- |
| Traffic, capture, timestamps | Real: lab VM traffic on `enp0s8`, AF_PACKET kernel receive times from the server only. |
| Feature extraction, windowing | Real: the same pipeline as replay, run on live frames. |
| Prediction | Real inference with a **synthetic demo model** (`data_kind: synthetic`). It shows the plumbing works; it is not evidence of detection accuracy. Lab rates overlap between benign and attack in the policy study, so no threshold is validated. |
| Dashboard | A terminated audit log is served as a recorded monitor run. Packet rates and aggregate decisions come from the recorded windows. Byte rate is unavailable because these logs omit it. A capture that ended unavailable retains that status. |

To review a finished run locally, start the dashboard API with the saved audit file:

```sh
python -m ddos_detector.api --audit-log results/run.jsonl --port 8002
```

Open [the dashboard in API mode](http://127.0.0.1:8002/frontend/?source=api). The API reads the file at startup, checks the run lifecycle and model provenance, and serves bounded history. Incomplete or invalid files are rejected before the server starts.

Raw captures stay under `data/lab-runs/` outside Git.

## Model and input contract

One model is loaded and validated at startup, then kept fixed in memory for the run. Hash, feature order, schema, threshold and runtime compatibility are checked by the existing model loader. Restart the runner to adopt a different package; changing files on disk does not hot-swap a running model. `--window` must be one second to match the version-one model. Duration, if supplied, must be finite and positive. Capped/empty/invalid windows are recorded as unscored with reasons; unavailable values are not benign predictions.

## Audit records and failure semantics

The exclusive-create, flushed JSONL file has two `record_type` values:

- `window`: window timestamps, selected packet count, audit time, score/decision when available, or an explicit not-scored reason. Model identity and synthetic/real provenance accompany successful predictions. `monitor_only` is always true. Processing delay is meaningful only for live input; replay reports null.
- `monitor_status`: start and terminal processing status, model identity/provenance, counts, skips, late drops, discarded partial windows and explicit capture gaps. Replay corruption and source failure end with unavailable status and nonzero exit. Backlog remains null. Kernel packet/drop counters are measured when live capture ends; they remain null for replay or a failed counter read. A completed processing run does not prove capture completeness. If the log itself fails, stderr/exit status are the remaining failure signals.

Consumers must filter by record type. A missing/old terminal state or an old last-window timestamp is not evidence of healthy current capture. Finalized records may remain after failure, but incomplete windows are discarded. Nothing in this log confirms active protection.

## Ayden's integration decision

Use direct validated delivery to a backend-owned state store. The monitor accepts an optional in-process delivery callback and sends window and lifecycle events after each audit write. The API pairs each window event with its original aggregate record for rates. A separate capture process or VM needs a transport adapter.

See [Backend replay and freshness](api-contract.md#backend-replay-and-freshness) for the replay server, history limits and response metadata.

## Lab load test (November 17)

Run on the lab server with the synthetic demo model, started with `scripts/monitor-start.sh`. One attacker VM (hping3 SYN) and one client VM (130 HTTP requests) were used. Each row is one run.

| Run | Attacker sent | Windows scored | late_dropped | max delay | kernel_packets | kernel_drops | Monitor CPU |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Quiet | 6,000 SYNs (about 200/s requested) | 55 of 55 | 0 | 1.317 s | 19,307 | 0 | not recorded |
| Rung 1 | 20,000 SYNs in 32.0 s (about 625/s) | 44 of 44 | 0 | 1.315 s | 61,308 | 0 | 3% average, 132 MB |
| Rung 2 (flood) | 2,649,857 SYNs in 20.0 s (about 132,000/s) | 63 of 63 | 0 | 1.297 s | 711,352 | 1,817 | peak 48% of one core |

During the flood the server VM was 14% to 19% user and 62% to 64% system CPU, with 19% to 22% idle. The server NIC counters since boot showed 0 errors, 0 dropped and 0 missed with 464,088 packets received. The attacker sent far more packets than the server's capture socket counted, so most of the loss happened before the server NIC (on the attacker VM or the virtual network; not located). `kernel_drops` counts only losses at the capture socket, so in a flood it understates real loss and should be read as a floor.

Limits: one run per row, synthetic model, one attacker, VirtualBox networking. hping3's timer tops out near 625 packets/s without flood mode. These numbers describe this lab only, and backlog is still not measured.
