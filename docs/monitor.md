# Monitor-only runner and backend handoff

The runner connects the existing frame/window pipeline to a trusted saved model. It does not attribute sources, request blocks or contact a firewall. Current use is a replay/integration check; real model readiness and real-NIC validation remain separate.

```powershell
python -m ddos_detector.monitor --replay tests/fixtures/week2/synthetic-mixed-boundaries.pcap `
  --victim 10.10.10.10 --model results/demo-model --log results/monitor-demo.jsonl
```

Use a model package generated by the project's training command, a fresh log path and an existing output parent. A synthetic package is explicitly labelled `data_kind: synthetic` in the output. This example does not measure real detector accuracy. Linux `--interface` capture requires the documented lab permissions and verified interface; it has not been run on a real NIC in this review.

## Model and input contract

One model is loaded and validated at startup, then kept fixed in memory for the run. Hash, feature order, schema, threshold and runtime compatibility are checked by the existing model loader. Restart the runner to adopt a different package; changing files on disk does not hot-swap a running model. `--window` must be one second to match the version-one model. Duration, if supplied, must be finite and positive. Capped/empty/invalid windows are recorded as unscored with reasons; unavailable values are not benign predictions.

## Audit records and failure semantics

The exclusive-create, flushed JSONL file has two `record_type` values:

- `window`: window timestamps, selected packet count, audit time, score/decision when available, or an explicit not-scored reason. Model identity and synthetic/real provenance accompany successful predictions. `monitor_only` is always true. Processing delay is meaningful only for live input; replay reports null.
- `monitor_status`: start and terminal processing status, model identity/provenance, counts, skips, late drops, discarded partial windows and explicit capture gaps. Replay corruption and source failure end with unavailable status and nonzero exit. Backlog and kernel drops are null because they are not measured; a completed processing run does not prove capture completeness. If the log itself fails, stderr/exit status are the remaining failure signals.

Consumers must filter by record type. A missing/old terminal state or an old last-window timestamp is not evidence of healthy current capture. Finalized records may remain after failure, but incomplete windows are discarded. Nothing in this log confirms active protection.

## Ayden's integration decision

**Use direct validated delivery to a backend-owned state store for the future API. Keep JSONL as an audit/replay artifact, not the live API's primary database.** In a single Python process, the orchestrator can load/construct `Monitor`, call `handle(record)` and ingest its returned window event into the store; status returns its event too. Keep the ingestion step explicit and bounded. A separate capture process/VM will need a defined IPC/transport adapter; a Python return value alone does not cross that boundary.

The future API maps the store into the existing metrics/detections/blocks/health contract, with freshness and failure handling. This PR does not implement that store, transport or API, and the current frontend remains in demo mode. JSONL is still useful for later review and deterministic replay, with provenance retained. Do not let the frontend read model packages or raw capture logs directly, and do not infer firewall state from predictions.

## Verification and remaining lab evidence

Offline tests exercise replay, no-overwrite/model refusal, model reuse, incompatible settings, capped windows and durable failure/gap events. `score_record` keeps its original behavior; the runner uses the same scoring guard with its already validated model package. Real AF_PACKET operation, capture drops/clock behavior, processing performance under load, store/transport integration and real-data scoring remain pending. No real data was trained or live traffic generated in these checks.
